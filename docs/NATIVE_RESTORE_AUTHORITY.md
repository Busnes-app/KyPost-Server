# Fresh identity authority after native restore

Historical baseline review at KyIdentity `8cf7cf9f424e14eaf9d7bea8e822af904f779528` and KyPost `50e60bc4a1e640a6b783152b831b7d53474f4d1d`. The recovery exporter added later is described below. Neither these findings nor the exporter enable native restore activation.

Current offline restore qualification now removes native device/browser push registrations and CardDAV app-password hashes and rotates subscriber IDs before publication; mail, pull history and users/wrapped-key documents remain retained. This revokes historical registration and CardDAV authority, including outstanding pairing tokens. Native CardDAV additionally rejects held accounts on both cached and fresh Basic auth; contact data remains retained. It does not establish complete fresh account/role authority or authorize fresh enrollment/hold release; see the [restore implementation](../backend/internal/backup/native.go) and [restore procedure](RESTORE.md).

Offline quarantine also raises existing published native subjects’ directory `RevokedBefore` cutoffs atomically, after strict epoch and historical ownership validation, to at least fence time plus 31 seconds. The shared verifier accepts at most 30 seconds of future issuance skew; browser and native admission refuse earlier issuance. Higher cutoffs, signed resources, activity, roles and legacy subjects remain intact. This is an issuance fence only; fresh primary authentication, local credentials/MFA, current authority and activation remain separate gates.

## Existing usable pieces

- KyIdentity's protected `POST /api/admin/systems/{id}/resync` queues a resync and returns success; it does not wait for downstream delivery or return a complete snapshot manifest. The store reconciles current access first, then force-queues active users and current groups in one transaction. Force-active users use `user.created`, intended to recreate a missing suite account. [Route and handler](https://github.com/Busnes-app/KyIdentity-server/blob/8cf7cf9f424e14eaf9d7bea8e822af904f779528/internal/api/server.go#L245-L258), [store resync](https://github.com/Busnes-app/KyIdentity-server/blob/8cf7cf9f424e14eaf9d7bea8e822af904f779528/internal/store/provisioning.go#L432-L493).
- Every queued desired-state write increments a per-system/per-resource revision, including forced resync. The dispatcher publishes that revision as SCIM `meta.version` and explicitly includes an empty role list when appropriate. A resync therefore supplies newer active-user evidence rather than merely replaying an old revision. [Revision allocation](https://github.com/Busnes-app/KyIdentity-server/blob/8cf7cf9f424e14eaf9d7bea8e822af904f779528/internal/store/provisioning.go#L151-L183), [wire metadata](https://github.com/Busnes-app/KyIdentity-server/blob/8cf7cf9f424e14eaf9d7bea8e822af904f779528/internal/sync/sync.go#L406-L424).
- Active-user resync payloads carry roles scoped to the paired app when that app defines roles, otherwise the legacy global role. Effective access requires a currently active, unexpired user, enabled app/client, and an applicable direct/group assignment or all-active-users policy; administrators receive no implicit bypass. [Role projection](https://github.com/Busnes-app/KyIdentity-server/blob/8cf7cf9f424e14eaf9d7bea8e822af904f779528/internal/store/app_roles.go#L448-L470), [access predicates](https://github.com/Busnes-app/KyIdentity-server/blob/8cf7cf9f424e14eaf9d7bea8e822af904f779528/internal/store/app_access.go#L11-L16), [live expiry views](https://github.com/Busnes-app/KyIdentity-server/blob/8cf7cf9f424e14eaf9d7bea8e822af904f779528/internal/store/app_access.go#L57-L65).
- KyPost verifies signed sync transport and issuer configuration, applies only a strictly higher directory revision, deactivates/revokes inactive accounts and revokes sessions on role changes. Equal revision with identical digest is acknowledged without reapplying the user mutation. [Signed ingestion](https://github.com/Busnes-app/KyPost-Server/blob/50e60bc4a1e640a6b783152b831b7d53474f4d1d/backend/internal/api/sync_handlers.go#L34-L79), [revision fence](https://github.com/Busnes-app/KyPost-Server/blob/50e60bc4a1e640a6b783152b831b7d53474f4d1d/backend/internal/sso/directory.go#L182-L220), [account mutation](https://github.com/Busnes-app/KyPost-Server/blob/50e60bc4a1e640a6b783152b831b7d53474f4d1d/backend/internal/api/sync_handlers.go#L126-L176).

## Why resync alone cannot release a restored server

- Resync explicitly selects only active user desired-state rows. Reconciliation queues losses when a recorded active row loses effective access, but an already inactive row whose offboarding was acknowledged need not generate another inactive event. Thus a backup taken before that offboarding can retain an active local account while a subsequent ordinary resync sends no fresh event for it. A synthetic real-store check at the pinned KyIdentity commit reproduced both already-acknowledged offboarding and deletion: after `ResyncSystem`, only the still-active control subject receives a new event; the removed subject receives none. This uses actual assignment, delivery claim/completion and resync methods, not live signed network delivery. [Active-only resync](https://github.com/Busnes-app/KyIdentity-server/blob/8cf7cf9f424e14eaf9d7bea8e822af904f779528/internal/store/provisioning.go#L450-L476), [loss reconciliation](https://github.com/Busnes-app/KyIdentity-server/blob/8cf7cf9f424e14eaf9d7bea8e822af904f779528/internal/store/provisioning.go#L285-L330).
- `GET /api/admin/systems/{id}/provisioning` exposes useful current per-system `desired`, recorded/acknowledged state, revision and delivery diagnostics. It is an admin paginated diagnostic, not an app-role/account snapshot: rows are drawn from existing users, omit deleted user identities, omit role lists and revocation cutoffs, and lack a stable whole-snapshot generation across pages. It cannot establish complete recovery authority by itself. [Handler](https://github.com/Busnes-app/KyIdentity-server/blob/8cf7cf9f424e14eaf9d7bea8e822af904f779528/internal/api/reconcile_handlers.go#L12-L28), [fields and query](https://github.com/Busnes-app/KyIdentity-server/blob/8cf7cf9f424e14eaf9d7bea8e822af904f779528/internal/store/reconcile.go#L610-L669).
- Inbound `GET /scim/v2/Users` is the upstream connector's imported directory, scoped by `source_connector_id`; it is not the outgoing KyPost app assignment directory. Its active flag combines source-active/local-disable, its version is the account update timestamp, and its response does not project outgoing app roles. Using this endpoint for native resume would cross the wrong authority boundary. [Inbound resource and list](https://github.com/Busnes-app/KyIdentity-server/blob/8cf7cf9f424e14eaf9d7bea8e822af904f779528/internal/api/scim_inbound_handlers.go#L189-L283), [connector scoping](https://github.com/Busnes-app/KyIdentity-server/blob/8cf7cf9f424e14eaf9d7bea8e822af904f779528/internal/store/scim_inbound.go#L302-L348).
- KyIdentity's reconcile readback reads generic remote SCIM targets. Suite webhooks explicitly have no read contract; this is not a fresh KyIdentity-to-KyPost authority export. The separate admin provisioning-resume API acknowledges operator judgment without reconciliation; it does not supply the missing evidence. [Readback scope](https://github.com/Busnes-app/KyIdentity-server/blob/8cf7cf9f424e14eaf9d7bea8e822af904f779528/internal/sync/reconcile.go#L102-L111), [operator resume](https://github.com/Busnes-app/KyIdentity-server/blob/8cf7cf9f424e14eaf9d7bea8e822af904f779528/internal/api/reconcile_handlers.go#L45-L59).

## Recovery prerequisites implied by these facts

A safe release needs fresh authenticated authority covering every restored issuer/subject, including current inactivity or authoritative absence for users already offboarded/deleted, current role projection and a new credential-revocation fence. Ordinary resync remains incomplete. KyIdentity now supplies an app-specific snapshot for an explicitly requested subject set; KyPost can record challenge-bound evidence and durable revision barriers through protected admin APIs. A separately confirmed repair API now reconciles published native activity/roles and revokes transport credentials while held. Restore-hold release remains unimplemented.

### Available exporter and the consumer boundary

[KyIdentity PR #73](https://github.com/Busnes-app/KyIdentity-server/pull/73) merged into actual `master` at `aacfa19de4eee34d3cb3a71f1f2d04cbe01e237d`; its implementation is pinned at `432ab5b09b2e94dd797a801cdcd1fcad8cd04971`. Protected `POST /api/admin/systems/{id}/recovery-evidence` requires an administrator, method/path-bound step-up and CSRF. It accepts a canonical 64-character lowercase hexadecimal challenge and 1–256 unique bounded ASCII subject IDs. A single transaction reads current app access, live expiry and app roles, including explicit inactive profiles for absent/deleted/offboarded subjects. It signs the exact bounded JSON bytes for purpose `recovery.evidence`, with event ID equal to the nonce, and returns nothing before the export audit commits. The version-1 envelope binds issuer, connection ID, nonce and a five-minute lifetime. [Handler](https://github.com/Busnes-app/KyIdentity-server/blob/432ab5b09b2e94dd797a801cdcd1fcad8cd04971/internal/api/recovery_evidence.go), [transaction and envelope](https://github.com/Busnes-app/KyIdentity-server/blob/432ab5b09b2e94dd797a801cdcd1fcad8cd04971/internal/store/recovery_evidence.go).

- `revision` is the observed per-subject delivery-ledger revision, nullable when unknown. Export does not allocate a new revision. Live expiry can change the snapshot profile without a revision increment; do not replace a queued `DirectoryUser`, manufacture `meta.version`, or reuse its digest from this profile.
- A KyPost challenge binds the current restore epoch, configured issuer, explicitly approved KyIdentity connection ID, selected current signing-key fingerprint and complete retained subject set. Current SSO settings do not retain that connection ID; never learn trusted connection/key identity from the uploaded evidence itself. Verification uses the selected pairing key, without ordinary sync's client-secret fallback.
- The consumer persists complete verified evidence and single-use challenge consumption atomically; new revision barriers cover only unpublished native reservations with no local account matching mailbox ID or subject. It applies the barrier before the ordinary event-ID replay shortcut and rechecks the challenge's epoch and retained-authority inputs under the existing disk fences; lower/unknown revisions, changed inputs, incomplete subject coverage and empty/invalid epochs cannot qualify recovery. Newer ordinary evidence invalidates the recovery qualification.
- Recovery evidence is a separate signed purpose, not a directory mutation or hold-release grant. `TestNativeRecoveryEvidenceCannotApplyDirectoryState` signs both a mirrored exporter envelope and a valid SCIM user with this purpose, exercises the real KyPost webhook, and checks exact account/lifecycle/hold preservation. Its ordinary-sync control verifies refusal does not consume the event ID. This is a synthetic boundary regression, not exporter-to-consumer or live recovery qualification.

### Protected consumer procedure

Challenge/import records evidence only. The separate repair step below changes existing native activity/roles and revokes transport credentials; neither import nor repair grants live access, makes a receipt current forever, or releases `native-restore-hold.json`. Use a live administrator session through the protected HTTPS origin and the existing CSRF/account-confirmation flow. A local recovery administrator must already be usable; this does not add an authentication bypass for held SSO accounts. Never post credentials, tokens or evidence profiles in issue/chat logs.

1. Exclusively restore/quarantine offline with all API/daemon/receiving workers stopped, then start the held server for protected administration. Never run offline restore/quarantine concurrently with these endpoints. Missing, old, empty, malformed, public-readable or nonregular hold epochs refuse evidence qualification; preserve staging and repeat the supported offline restore procedure.
2. Explicitly approve the current KyIdentity paired system ID and the SHA-256 fingerprint of the selected current pairing secret. Hash the exact UTF-8 runtime signing-secret string: a selected `PAIRING_SECRET` override is trimmed; the generated `pairing.key` contributes the standard-base64 encoding of its raw key bytes. `sha256sum pairing.key` is not that fingerprint. Compute it locally without printing the secret. Do not take either trusted value from an uploaded export. `POST /api/admin/native-recovery/challenge` accepts `{systemId,keyFingerprint,password}` or `{systemId,keyFingerprint,authSecret}`; KySignOn sessions use the existing exact-request step-up flow instead of a local password. A new challenge replaces prior qualification and lasts 15 minutes. Its ordered `subjects` cover retained configured-issuer directory rows (including resource-less/inactive rows), native reservations, local linked subjects and prior revision-barrier subjects. Unsupported or inconsistent ownership/identifiers refuse; no subject is silently dropped.
Mailbox limits are retained authority: restarting with a different `KYPOST_MAILBOX_QUOTA_BYTES` (which `migrate-native` applies to every mailbox) between the challenge and the repair changes the authority digest and voids the recorded evidence. Keep the quota fixed until the repair completes, or start a new challenge. See [mailbox quotas](NATIVE_PROVISIONING.md#mailbox-quotas).

3. Pass the returned nonce and exact subject list to KyIdentity's protected exporter for that explicitly approved system. Preserve its exact response body and all four signature headers. The five-minute signed evidence must still be live on import; clocks must agree closely and no retained authority may change between challenge and import.
4. `POST /api/admin/native-recovery/evidence` accepts `{bodyBase64,signature,timestamp,eventType,eventId,password}` or the corresponding `authSecret` credential. `bodyBase64` is canonical standard base64 of the exact response bytes, not reformatted JSON. The four fields contain the export's `syncauth` header values. The wrapper is bounded to 384 KiB and decoded evidence to 256 KiB; the ordinary action-digest cap stays 64 KiB for other routes. Successful import returns `evidenceRecorded:true`, `accountsRepaired:false`, `restoreHeld:true`. That response acknowledges storage, never current recovery readiness or delivery.
5. While the original signed evidence is still live, separately confirm `POST /api/admin/native-recovery/repair` with `{password}` or `{authSecret}`; KySignOn uses a new exact-request step-up. Supply no account plan or replacement evidence. The server verifies the stored receipt, complete retained authority, current key/epoch and existing native storage. It confirms the usable legacy administrator once, then rechecks the same account/settings/session witnesses through account publication and again before completion. A durable intent and native-only revision barriers precede the atomic activity/role write; ordinary directory desired state/revisions are not replaced. Legacy accounts, passwords, SSO-link revocation flags, mail, labels and PGP material remain retained.
6. Cleanup removes native sessions, native device/push registrations, outstanding pairing authority and CardDAV app passwords before recording completion. Browser-push subscriptions are removed by the separate offline restore procedure. `200 {accountsRepaired:true,restoreHeld:true,accounts:N}` means that repair completed while held, not that receiving/sending or enrollment is ready. A `409` can follow committed account changes or partial credential cleanup; preserve the hold, resolve storage/cleanup failures, sign in again and obtain a new challenge plus complete signed evidence. Repeating an old repair does not retry its journal. The 30-second context bounds cooperative stages; blocking cleanup locks/filesystem/SQLite calls can take longer.

The owner-only lifecycle JSON retains the exact signed body and headers separately from ordinary directory resources. On evidence import alone, signed profiles may reflect live expiry at an unchanged observed revision; they never replace `DirectoryUser`, `meta.version`, account roles or activity. Nullable, nonpositive or lower observed revisions refuse. Receipt, one-use consumption and eligible unpublished-reservation barriers commit in one atomic write under settings → directory → fresh users fences. Confirmation's account revision/credential witnesses and live unexpired session/admin ceiling are checked again before that write; the private account epoch covers all existing users, including a local administrator's deactivate/reactivate cycle.

Published native and legacy accounts continue ordinary offboarding and demotion at the exported observed revision; held native accounts cannot exercise login/session/admin authority. Retain a separate legacy recovery administrator. Credential revocation can delete devices and rotate subscriber IDs while held through an uncached, existing-only ownership-validated opener. Ordinary mail/maintenance admission stays held; missing or mismatched storage refuses revocation and leaves its event retryable.

Prior barriers are retained. If a published account matches a prior barrier by subject or reserved mailbox ID, qualification refuses unchanged unless its durable directory revision is strictly above the barrier or exact native repair provenance binds that issuer/subject/mailbox/source and floor. Historical repair provenance may survive a later offline restore epoch because it supplies ordering only; it never proves current access. Unsupported, missing or mismatched provenance still refuses, including for legacy owners. Preserve unsafe preview artifacts or partial-publication state and retry a genuinely newer signed event; never delete the barrier to qualify. Unlinked accounts occupying reserved IDs also invalidate outstanding challenges.

Ordinary events at or below an installed barrier refuse even if their event ID was previously acknowledged. Request a genuinely newer upstream revision/resync for blocked queued events; do not lower barriers or synthesize a revision. A newly accepted configured-issuer event invalidates the receipt/challenge; prior barriers remain. Expired or invalidated receipts are historical evidence only. Any future status/release implementation must recompute epoch/settings/key/subject/ownership/account validity and expiry rather than trust receipt presence. Changing account/settings inputs does not become an access grant, and starting another challenge never removes barriers. No GET readiness/status or automatic repair/release exists.



Repair intents bind the exact receipt and explicit before/after authority digests. Historical native provenance barriers survive later restore epochs only as ordering metadata. Completion requires the exact resulting state, original signature, current key/epoch/expiry and intact storage. New challenges or newer issuer events invalidate the journal while keeping ordering barriers. The original receipt continues to bind pre-repair authority; account changes do not make it proof of the resulting state. No readiness/status or hold-release endpoint is supplied.

Identity reconciliation alone is insufficient: KyPost's documented restore contract additionally requires fresh domain/receiver/relay evidence, prevention of stale message IDs resolving to newly allocated mail, and quarantine of restored queued/interrupted/uncertain outbound work. The hold currently has no automatic release. [Restore contract](https://github.com/Busnes-app/KyPost-Server/blob/50e60bc4a1e640a6b783152b831b7d53474f4d1d/docs/RESTORE.md#L132-L140), [hold guard](https://github.com/Busnes-app/KyPost-Server/blob/50e60bc4a1e640a6b783152b831b7d53474f4d1d/backend/internal/sso/native_restore.go#L18-L30).
