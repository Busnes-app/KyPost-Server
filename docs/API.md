# API Highlights

- Public `GET /api/installer/network` returns only client IP, proxy trust and the effective security scheme for edge verification. It uses the product’s configured-origin security fallback; see [installer setup](INSTALLER_SETUP.md).

- Admin backup routes: `GET /api/admin/backup/status`; `POST` to `run`, `export-capsule`, `drill`, `pair-remote`, `pin-key`; `DELETE pairing`; `PUT schedule` under `/api/admin/backup/`. Mutations require the current account credential and CSRF protection, or, for a session signed in through KySignOn, a fresh KySignOn confirmation of that exact action.

Auth:

- `POST /api/auth/login` — body `{username, authSecret, captchaToken?}`. The server never accepts the password; an account still holding a pre-derived-auth hash is refused like an unknown user until an admin resets it.
- `GET /api/auth/login-params` — the per-account salt and work factor a client
  needs to derive its auth secret, so the password is never transmitted. Public,
  and deliberately answers identically for a username that does not exist.
- `GET /api/auth/captcha-config`
- `GET /api/auth/pow-challenge` (`CAPTCHA_PROVIDER=pow` only)
- `GET /api/auth/csrf`
- `GET /api/auth/me` (includes `hasPassword`, false for an SSO-only account, and `encryptionSetup` `{required, offered, hasKey, hasRecovery, incomingEnabled, keyPolicy, incomingPolicy}`; see [first sign-in setup](E2E_PGP.md#first-sign-in-setup); a hosted (multi-tenant) export-only session adds `exportOnly: true` and reaches only the export routes)
- `POST /api/auth/logout`
- `GET|POST /api/auth/password` (read a private password-change snapshot, then atomically commit credential and optional PGP rewrap; forced resets preserve the previous sealed key for recovery)
- `POST /api/auth/step-up` (body `{authSecret, code}`: re-confirms the account credential, and a second factor when one is enrolled, before the Security page renders; a session signed in through KySignOn confirms with KySignOn instead, see below)

Single Sign-On (OpenID Connect):

- `GET /api/auth/sso-config` — public `{enabled, issuerUrl, clientId}` that gates the sign-in button and native sign-on. Never returns the client secret.
- `POST /api/auth/native/signon` — body `{idToken, proofKey, proof}`: a KyIdentity device-grant ID token, refused unless its `origin` claim matches `SERVER_BASE_URL`, plus proof of the app key its `cnf.spki#S256` names (format in [native sign-on](PLATFORM_BASELINE.md#1-pairing)). A token without `cnf` answers 403 "Update KyAuth and KyIdentity to sign in from this app."; any proof failure answers 403 "Access denied: the sign-in proof does not match." Both refusals come before the token's single use is spent. No setting turns the proof off. Requires SSO plus `PAIRING_SECRET` and `SERVER_BASE_URL`, otherwise 503. Answers the same single-use 90-second pairing deep link as review-pairing. Its token is returned to the app directly, so the device it registers needs no [approval](device-approval.md).
- `GET /api/auth/oidc/login` (alias `/auth/sso/login`) — starts the authorization-code flow for signing in. Metered per IP on the login-params bucket (429 with `Retry-After`); the callback that redeems a state this route issued is not charged again, any other callback is.
- `POST /api/settings/sso/link` — links the provider identity to the *caller's own* account. Requires the account credential (`authSecret`, and the two-factor code, when one is enrolled) re-entered now, because a linked identity is a way to sign in.
- `GET /api/auth/oidc/callback` (alias `/auth/sso/callback`) — verifies the ID token, including a positive issuance timestamp no more than 30 seconds ahead of the server, then signs in, auto-provisions, or links by `sub`. Keep issuer/server clocks synchronized. The session remembers the provider's `sid`, so the provider can end it.
- `POST /api/auth/oidc/step-up`, `GET|DELETE /api/auth/oidc/step-up/{id}` — action-bound re-authentication for a session signed in through KySignOn. A sensitive request (the Security page gate, backup actions) answers `403 {"error":"sso_step_up_required","challenge":…}`; the browser opens a KySignOn sign-in popup for that one action (`prompt=login`), and repeats the request with `X-Kypost-Step-Up: <challenge>` once it is verified. The grant is spent once, for that request only.
- `POST /api/auth/oidc/backchannel-logout` — OpenID Connect back-channel logout receiver. Register it at the provider (KySignOn: the client's *back-channel logout URI*). The `logout_token` is verified against the issuer's JWKS, admitted once durably, and ends the session it names, or every session of the subject when it names none. Needs an `https` issuer.
- `POST /api/settings/sso/unlink`
- `GET|PUT /api/admin/sso` (admin only. The provider configuration. The client secret is write-only: responses carry `clientSecretSet`, and a blank secret on `PUT` keeps the stored one only for the same issuer and client ID. `PUT` needs the step-up below. Saving a different issuer revokes every account link made at another provider; those users link again. `adminGroup` is the exact group or realm role that makes a generic provider's new account an administrator; empty, none does.)
- `GET|PUT /api/admin/encryption-policy` (admin only. `{key: required|optional, incoming: required|on|off}`, default `required`/`on`; responses add `genericProvider` and `issuer`. `incoming: required` also sets `key: required`. `PUT` needs the step-up below and is audited; Required is refused with `409 {"code":"kysignon_required"}` while the SSO provider is not KySignOn. [Contract](E2E_PGP.md#first-sign-in-setup).) `PUT /api/admin/sso` enabling a provider that is not KySignOn while either setting is Required answers `409 {"code":"encryption_policy_required"}` naming what to lower.
- `GET|PUT /api/admin/rate-limit-networks` (admin only. Office networks whose requests skip the per-address sign-in limits; see [SECURITY.md](../SECURITY.md#office-networks-rate-limit-allowlist). Returns `{networks, environment, exempted}`: the stored list and `RATE_LIMIT_EXEMPT_CIDRS`, both comma-separated and canonical, and the requests that skipped a limit since the last change or restart. `PUT {"networks":"203.0.113.0/24,2001:db8:1::/48"}` (empty clears) needs the step-up below; an invalid entry, a range broader than /16 or /48, loopback or more than 256 networks is refused with 400 and the reason. Takes effect at once and is logged.)
- `POST /api/calendar/itip/send` — KyCalendar asks KyPost to mail an iTIP REQUEST, CANCEL or REPLY from the user's own mailbox. No session: a `syncauth` signature under the shared KyCalendar secret, event type `kycalendar.itip.send`. 404 when KyCalendar is not configured. Answers `202 {"outcome":"sent"}` or `{"error","code"}`; codes and checks in [KYCALENDAR.md](KYCALENDAR.md#send-kycalendar--kypost).
- `POST /api/sync/hr-mailbox` — signed `hr.mailbox.reserve` request from the configured KyIdentity issuer. Reserves a native work-email address for a future immutable SSO subject, with no account/access grant. See [request, response and retry contract](NATIVE_PROVISIONING.md#hr-address-reservations).
- `POST /api/suite/kypulse/alert` — KyPulse asks KyPost to send one plain-text alert from a member's mailbox. No session: a `syncauth` signature under the KyIdentity pair secret, event type `kypulse.alert.send`. 404 `kypulse_off` when not paired. Answers `202 {"outcome":"sent"}`, `200 {"outcome":"duplicate"}` or `{"error","code"}`; body, checks and codes in [KYPULSE.md](KYPULSE.md#send-kypulse--kypost).
- `POST /api/sync/webhook` — KySignOn directory push. Pair KyPost in KySignOn as a webhook system with this URL and either the pairing secret or the SSO client secret as the sync secret. Each event is a signed, versioned SCIM User; stale or reordered deliveries are refused, a disabled or deleted user keeps their mailbox and loses access, and a rehire brings the same account back. `user.mfa_reset` applies desired membership and revokes the subject’s sessions, devices, pending pairing authority, CardDAV app passwords and agent tokens while keeping the SSO sign-in link. It shares the org-binding, replay and revision checks; a replay leaves newly issued credentials alone. After successful cleanup its token cutoff covers the current second plus the accepted 30-second issuer skew; a fresh sign-in may need to wait up to 31 seconds. Supported SCIM fields (including email `type`) are retained durably alongside the revision fence for later repair; acknowledgment does not mean a domain mailbox or receiver route is ready. A hosted (multi-tenant) install also accepts `user.erased`, a removal that then purges that member's data; a self-hosted install refuses it as before.

Config and data:

- Scheduled send: `POST /api/mail/send` and `POST /api/mail/send-pgp` take an optional `sendAt` (RFC 3339, one minute to 366 days ahead) and answer `202 {"scheduled":true,"id","sendAt"}` instead of sending. The message is built and frozen then, dated `sendAt`. Refused when scheduling: calendar replies, recipients without a key (no pickup link is ever scheduled) and mail without a To. A client-custody account must send its encrypted draft (`pgpDraft` on `/api/mail/send`, `draftCopy` on send-pgp, whose every delivery `Date` must be within a minute of `sendAt`); an encrypted `/api/mail/send` without one returns to Drafts as its self-encrypted Sent copy, and is refused without a key of your own. At most 50 pending and 256 MiB of pending data per user (409); a single message over 128 MiB is refused (413). If the password, two-factor, role, sign-in, PGP keys or keyring generation, sending device, send-as alias or IMAP account changed by then, the message is not sent and returns to Drafts with a reason. A definite SMTP refusal retries every 5 minutes until an hour after `sendAt`, then returns to Drafts; an unconfirmed acceptance becomes `uncertain` and is never retried. Native mailboxes enter the outbox only when due (status `queued`; `GET /api/mail/outbox/{id}` with the same id).
- `GET /api/scheduled` — the selected mailbox's scheduled mail: `{scheduled:[{id,status,reason,sendAt,subject,to}]}`, status `scheduled|sending|returning|returned|sent|queued|uncertain|failed`. Subject is the encrypted-placeholder for browser-encrypted mail. Final rows are kept 30 days.
- `POST /api/scheduled/{id}/cancel` — returns a `scheduled` message to Drafts (200, or 202 with `warning` when the draft save is retried later); 409 once sending has started; 404 for another user's or mailbox's id.
- Send delay: `POST /api/mail/send` and `POST /api/mail/send-pgp` take an optional `sendDelay: true`. When the caller's setting (`GET /api/mail/send-delay`) is above 0 the message is held as a scheduled one going out at the end of the delay, and the answer is the scheduled `202` plus `"delayed":true`; with the setting Off, or without the flag, the send and its response are unchanged, so a client that does not know the delay keeps sending at once. The held message is dated when Send was pressed (send-pgp deliveries carry the browser's Date, unchecked as for an immediate send, and need `draftCopy`). It is not held, and goes now, when it is a calendar reply or an encrypted send with `allowPickupFallback`; a send with `sendAt` goes at that time with no delay added. An unreadable setting answers 503 and sends nothing. Cancel is `POST /api/scheduled/{id}/cancel` from any signed-in client (409 once release has started); a canceled message returns to Drafts and is never charged to the sending quota. Listings mark held rows `"delayed":true`.
- `GET /api/mail/outbox/{id}` — session/device-authenticated native delivery state for the acting owner, with attempts/retry timing and Sent status; no MIME or credentials. Native send replies add `outboxId`; success still requires confirmed primary SMTP acceptance. Inspect uncertain jobs before resubmitting. See [outbox contract](NATIVE_OUTBOX.md).
- `GET|PUT /api/admin/mail-relay` — admin-only encrypted domain relay settings. PUT accepts `{host,port,smtpUsername,smtpPassword,domains?,authSecret}` (`authSecret` is the acting account's derived credential), requires CSRF/request-bound step-up and fresh issuer-bound DNS proof of every newly added relay domain and of at least one domain overall, and defaults port to 465. Omitted `domains` keeps the saved set (the founding domain for a new relay); a body with only `domains` changes the set and keeps the generation; removing a domain with queued or retryable jobs is refused and moves it to `retiredDomains`. Responses redact both relay credentials and DKIM private keys and report configured native capability in `sendingEnabled` (not provider readiness); this native profile requires verified implicit TLS and AUTH. Responses carry `dkim` (empty for a relay); see the direct profile below. See [relay contract](DOMAIN_RELAY.md).
- `GET /api/admin/mail-relay/deliverability` — admin session, read-only, no step-up. For a saved direct profile (409 otherwise) checks each sending domain's `dkim`, `spf` and `dmarc` records and one `ptr` check for `host`: `{host, domains:[{domain, checks:[{check,name,status,message,found?}]}], ptr, egressObserved:false, mailSent:false}`, `status` ∈ `pass|warn|fail|unknown`. 5-second lookups, 30-second request, at most 16 reverse lookups, DNS text cut to 512 bytes; once per 10 seconds per instance, otherwise 429 with `Retry-After`. Creates no mail, outbox or audit state. See [direct delivery](DIRECT_DELIVERY.md#dkim-spf-dmarc-and-reverse-dns).
- `POST /api/admin/mail-relay/dkim/rotate` — `{domain, emergency?, acceptGap?, authSecret}` with CSRF, action digest and the relay PUT's step-up; refused under a restore hold (409). Normal: creates a `next` key (fresh `kypost-<8 hex>` selector) and returns it as `record` with the full relay status; repeating returns the same key and writes nothing; 409 for a relay profile or while a key is `retiring` ("finish the previous rotation first"), 404 for a domain outside `domains`. Emergency (needs `acceptGap:true`, else 400): a fresh key signs at once, any `next` is dropped, the old key becomes `removable` with no private key, and `warning` says mail fails DKIM until the new record is published. See [rotation](DIRECT_DELIVERY.md#dkim-key-rotation).
- `POST /api/admin/mail-relay/dkim/confirm` — `{domain, authSecret}`, same protection. Looks up the `next` record; 409 with the check status and remediation while it is not live, 200 with the relay status once it switches (old key `retiring` for 7 days). Shares the deliverability limit (one run per 10 s, else 429 + `Retry-After`).
- `POST /api/admin/mail-relay/test` — admin-confirmed no-mail check of the saved `expectedGeneration`, using the same strict TLS/AUTH policy as delivery. Fresh domain/issuer and restore gates run before and after connection; one check per instance per 30 seconds. No MAIL/RCPT/DATA or outbox writes; success reports `deliveryTested:false` and proves neither From authorization nor inbox placement. See [check contract](DOMAIN_RELAY.md#check-the-saved-relay-without-sending-mail).

IMAP and inbox:

- `GET|POST|DELETE /api/imap/config`, returns 403 while `managed`
- `POST /api/imap/test`
- `GET /api/inbox?limit=500&mailbox=<name>`. Add `bodies=0` to get the list without message bodies — 13.3 MiB against 3.1 KiB for a 500-message window, since the rows render no body. The web UI then preloads the current 20-message page one body at a time from `GET /api/mail/body`, so the list renders first and opening a displayed message normally needs no wait. See [docs/INBOX_PAYLOAD_HANDOFF.md](INBOX_PAYLOAD_HANDOFF.md). Add `before=<messageId>` for the next page of older mail (metadata only, with `hasMore`/`nextBefore`); see [docs/PLATFORM_BASELINE.md](PLATFORM_BASELINE.md) §7.
- `POST /api/admin/native-recovery/challenge` and `/api/admin/native-recovery/evidence` — administrator CSRF and exact-action confirmation bind one signed KyIdentity export to a usable restore epoch and complete retained subjects. Import preserves the hold and account state while installing durable revision barriers only for unpublished native reservations; published accounts retain ordinary offboarding/demotion. It grants no recovery readiness. See [protected recovery procedure](NATIVE_RESTORE_AUTHORITY.md#protected-consumer-procedure).
- `GET /api/admin/native-recovery/status` — administrator, read-only: each native restore hold release precondition with its reasons, the `KYPOST_NATIVE_RESTORE_RELEASE` flag, Cloudflare fence state and ordered next steps; never evidence contents. `kypost-server restore status`, run as the `STATE_DIR` owner, prints the same. See [reading release status](RESTORE.md#reading-release-status).
- `POST /api/admin/native-recovery/repair` — separately confirmed administrator repair using the current stored signed evidence. Reconciles existing native activity/roles, persists replay barriers before account writes, and revokes sessions, device/push, pairing and CardDAV credentials before recording completion. Legacy accounts and retained mail/PGP data are preserved. Partial failures keep the restore held and require fresh evidence; success also preserves the hold. See [protected recovery procedure](NATIVE_RESTORE_AUTHORITY.md#protected-consumer-procedure).
- `POST /api/admin/native-recovery/release` — off unless `KYPOST_NATIVE_RESTORE_RELEASE=true`. An unlinked local administrator on a password session confirms the credential; the server rechecks every release precondition under its fences and a fresh DNS proof, and on the bundled-receiver profile requires `"confirm": "original-host-decommissioned"`. It deactivates non-native accounts the evidence shows inactive, demotes non-native administrators it shows without the administrator role, writes release floors and ID-token fences, then renames the hold to `native-restore-released.json`. A repeat answers `alreadyReleased`. See [releasing the hold](RESTORE.md#releasing-the-hold).
- `GET|PUT /api/admin/mail-domain` and `POST /api/admin/mail-domain/verify` — admin-only mail-domain diagnostics/setup. Writes require CSRF and the current account credential (KySignOn uses request-bound step-up). Configure `{domain,authSecret}` after KyIdentity pairing, publish the returned exact TXT record, then verify with the same credential fields. These routes serve the founding domain. DNS proof binds one immutable domain/issuer, initial verification expires after 24 hours, and configuring again rotates the challenge. Once established, the same TXT record is rechecked automatically without daily DNS changes. System DNS is not DNSSEC; every allocation rechecks it. Explicit KYPOST_NATIVE_MAIL=true enables provisioning and local mailbox access after verified directory assignment; verification alone enables no reception or sending. See [setup and failure responses](NATIVE_PROVISIONING.md).
- `GET|POST /api/admin/mail-domains`, `POST /api/admin/mail-domains/{domain}/verify` and `DELETE /api/admin/mail-domains/{domain}` — admin-only domain set: list per-domain status (`configured`, `retired`, `recordName`, `recordValue`, `established`, `expiresAt`, `verifiedUntil`), add a domain or rotate its challenge with `{domain}`, verify one domain, and retire one (409 while an address on it is active, a queued/retryable outbox job sends from it, accepted (pending) incoming mail is bound to it or the relay still sends for it; address records are kept; re-adding a retired domain configures it afresh, and its addresses resume for their recorded mailboxes once it verifies again). Same CSRF, credential and step-up rules as the single-domain routes; each proof fences only its own domain. See [several domains](NATIVE_PROVISIONING.md#several-domains).
- `GET|POST /api/admin/mail-addresses`, `DELETE /api/admin/mail-addresses/{address}` and `POST /api/admin/mail-addresses/{address}/reassign` — admin-only native aliases: list mailboxes and their addresses (`address`, `kind`, `state`, `generation`; `?user=<id>` filters) with each mailbox's `usedBytes`/`quotaBytes` and a `storage` summary of quotas against the drive (`overcommitted` above 80%), add an alias with `{mailbox,address}` to an everyday identity's mailbox on a configured domain, release one (kept as `reserved`, never deleted) and reassign a reserved one with `{mailbox}`. Each change of owner or state moves the address to a new generation, so mail or outbox jobs frozen against an older one are quarantined, never delivered; ordinary KyIdentity edits change no generation. 400 malformed, 404 unknown, 409 taken/reserved/primary/a KyIdentity primary/administrator owner/unconfigured domain/restore hold; a committed change whose receiving-route update is still pending answers 200 with a `warning`. Same CSRF, credential and step-up rules as the domain routes. Users send from an active alias by naming it in `from`. New aliases holding a `+` are refused (400); existing ones keep working. A user's masked address is refused for release and reassignment (409): its owner pauses or deletes it. See [addresses](NATIVE_PROVISIONING.md#addresses-aliases-and-generations).
- `GET|POST /api/admin/mailboxes`, `POST /api/admin/mailboxes/{id}/disable` and `POST /api/admin/mailboxes/{id}/enable` — admin-only extra native mailboxes: list mailboxes with `kind` and `state` (`?user=<id>` filters), create one for an everyday identity with `{user,address}` (its primary address on an established domain, unique and not any KyIdentity primary; stored under `$STATE_DIR/mailboxes/`), and disable or re-enable it (mail is kept; its addresses stop routing and sending; jobs still queued in its outbox are quarantined). Listings carry `prepared`. Creation is 409 while the owner has incoming encryption on, and enabling incoming encryption is 409 while the user has an extra mailbox: it covers the primary only. Same gates and error mapping as the alias routes. See [extra mailboxes](NATIVE_PROVISIONING.md#extra-mailboxes).
- `GET /api/admin/receiving/cloudflare` — admin-only continuous Cloudflare receiving status: `running`, `fenced`, `error`, `uninitialized` or `not-started`, last published revision, last publish and pickup times, oldest waiting capture and its one-hour warning, waiting and ledger counts. Never addresses, envelopes or credentials.
- `GET /api/admin/receiving/quarantine[?after=<sequence>]`, `POST /api/admin/receiving/quarantine/{gateway}/{id}/release` and `POST /api/admin/receiving/quarantine/{gateway}/{id}/discard` — admin-only quarantined native deliveries: list up to 100 envelopes (gateway, ID, received time, envelope sender, size, and per recipient the address, frozen mailbox, owning user and generation; never body, subject or headers), release one to the mailboxes it was frozen to (refused with 409 and the reason when a frozen mailbox was deleted or disabled, changed owner or is no longer admitted; never to an address's current owner), or discard it (bytes removed, a tombstone blocks redelivery; `partially_released` when an interrupted release may already have reached some mailboxes). Release refusals say whether the cause is durable (discard remains) or transient (resync and retry). An `unresolved` delivery (continuous Cloudflare mail captured under a routing table this server does not know, typically after a restore) lists its address's owner today (`currentMailbox`, `currentUser`) and is released only with `{"toCurrentOwner": true, "currentMailbox": "<as listed>"}` to that owner (refused if the address moved since it was listed), not proven to be the original, while the address is active; that action is audited separately. POSTs need CSRF and the account credential or KySignOn step-up; every action is audited without content. See [quarantine release](NATIVE_PROVISIONING.md#quarantine-release).
- `GET|POST /api/admin/receiving/blocks` and `DELETE /api/admin/receiving/blocks/{id}` — admin-only sender blocks for both receiving profiles: list blocks in force (`id`, `kind`, `value`, `until` in Unix ms or null, `source` `manual` or `automatic`, `level`, `createdAt`, `actor`, `reason`) plus automatic-block `evidence` status (`damaged`, `resetAt`, `domainBlocksFrom`, `goodFull`, `automaticFull`), block an `address` or `domain` with `{kind,value,until?,reason?}` (reason `spam`, `phishing`, `abuse` or `other`; any sender either profile accepts, A-Z lowercased and non-ASCII compared exactly, A-labels for internationalized domains; domains match exactly, not subdomains; your own mail domains and addresses on them are refused with 409, and adding a mail domain a block matches is refused until you unblock it; at most 5000), or unblock one by its listed `id` (so proxy logs never record a blocked address; this also stops automatic re-blocking of it for 30 days; if that cannot be recorded the block is still removed and the answer carries a `warning`). Maddy answers blocked senders `550 5.7.1` at RCPT; the Cloudflare Worker rejects them from the signed table, republished within seconds. Already accepted mail is unaffected and the null sender is never blocked. POST and DELETE need CSRF and the account credential or KySignOn step-up; audited with the block ID, never the address. See [sender blocks](NATIVE_PROVISIONING.md#sender-blocks).
- `GET /api/mailboxes` — the caller's accessible native mailboxes (primary first) and their active addresses, with `usedBytes` (absent when unreadable) and `quotaBytes`; disabled ones are omitted. Mail routes accept an optional `X-KyPost-Mailbox` header naming one of them (absent means the primary, so older clients are unchanged); unknown, foreign and disabled mailboxes all answer the same 404. Per-user routes ignore the header, and native notifications carry the mailbox ID. See [mailbox selection](PLATFORM_BASELINE.md#native-mailbox-selection-additive).
- `GET /api/export/folders`, `POST /api/export` and `GET /api/export/{token}` — self-service export of the caller's own native mailbox or one folder as mboxrd or a zip of EML files, exact stored bytes (encrypted mail stays encrypted). Mail:

- Client-prepared `/api/mail/send-pgp` batches reject envelope recipients repeated across delivery groups (case-insensitive parsed addresses) with `400`, before sending, charging quota or scheduling. Distinct Bcc groups remain supported.
- Invalid SMTP recipient: immediate external-account `POST /api/mail/send` and `POST /api/mail/send-pgp` return `422 {"code":"invalid_recipient","error":"…"}` when the relay refuses RCPT with a permanent SMTP reply and enhanced status `5.1.1` (mailbox absent), `5.1.2` (domain unavailable) or `5.1.3` (bad address). The explanation names the submitted recipient and asks the sender to check it; provider reply text is not echoed. No DATA is sent for that delivery. Policy refusals, temporary failures and failures in other SMTP phases are not classified as invalid addresses. Later Bcc/secure-link failures keep the existing partial-delivery warning; native outbox and scheduled-send contracts are unchanged. Clients should display `error` as plain text and keep compose open for correction.
- Sending quota: every account may send `sendQuota.messagesPerHour` messages an hour and `sendQuota.recipientsPerDay` recipients (To, Cc and Bcc) a day, across `/api/mail/send`, `/api/mail/send-pgp`, send-as verification mail and out-of-office replies, defaults 60 and 1000, set in `PUT /api/config` or per account. ## Native direct outbound profile

`PUT /api/admin/mail-relay` accepts explicit `mode:"direct"` with an EHLO `host` and the proved domain set; port/credentials are omitted. GET adds `mode` and reports `transport:"mx-starttls"`, `authRequired:false`, `port:0`, `dkim:[{domain,selector,recordName:"<selector>._domainkey.<domain>",recordType:"TXT",recordValue:"v=DKIM1; k=rsa; p=<SPKI>"}]` one entry per key with `state` (`active|next|retiring|removable`) and `createdAt`; `active` adds `ageDays`, `rotationRecommendedAt` (`createdAt` + 180 days) and `rotationRecommended`; `retiring`/`removable` add `retiredAt` and `keepPublishedUntil`; `removable` has no `recordValue`; and `recommended` SPF (`v=spf1 a:<host> -all`) and DMARC (`v=DMARC1; p=quarantine; adkim=s; aspf=s`) records `{domain,kind,recordName,recordType,recordValue}`; it does no DNS I/O. Saving creates one DKIM key per sending domain that lacks one; keys are never returned. Existing administrator, CSRF, request-bound confirmation, generation and restore gates apply. Saved-relay login tests refuse direct profiles. [Direct delivery](DIRECT_DELIVERY.md) specifies egress/TLS and rollback.

Direct send responses preserve primary-acceptance `ok`/HTTP semantics and add `deliveryMode:"per-recipient"`, `deliveriesConfirmed`, `deliveriesTotal`; other recipients can have accepted even when the primary returns 503. Inspect each existing owner-scoped outbox sequence before resubmission. This is not a queued-success or exactly-once API.


### Spec A P3 OpenPGP compatibility

`POST /api/pgp/device/enrollment-key` and `POST /api/pgp/device/enrollment-state` both
accept optional `openpgp: ["v4","v6","rfc9980"]`, persisted for the authenticated device.
Omitted/null reports are legacy `["v4"]`; invalid/empty lists are 400. The native-device
list returns `openpgp` per device, separately from `enrollmentEnvelopeVersions`.
See [normalization and upgrade behavior](DEVICE_ENROLLMENT.md#normative-device-openpgp-capabilities-spec-a-p3).
Wrapped envelopes are bounded to 512 KiB and recovery files to 2 MiB. Complete-ring
snapshot metadata and existing rewrap/password/recovery writers accept ring versions
1 and 2, with the submitted version matching the current snapshot. Conversion is not
exposed. See [keyring v2](E2E_PGP.md#keyring-v2-reader-contract-spec-a-p3).
