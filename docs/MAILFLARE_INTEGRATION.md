# Mailflare integration feasibility

Status: candidate research only; no Mailflare integration is implemented or selected. The [turnkey mail stack plan](TURNKEY_MAIL_STACK_PLAN.md) defines current implementation scope and architecture.

## Product scope

The owning [AGENTS.md preference](../AGENTS.md#user-preferences) is a minimally configured domain mail appliance managed from KyIdentity. This report assesses one possible engine; neither integration nor a fork is selected. Existing directory sync creates/deactivates KyPost users and managed mail settings can supply credentials, but mailbox provisioning is missing. The [Maddy appliance proposal](MADDY_INTEGRATION_HANDOFF.md) explores this same boundary and is not shipped code. Engine choice should follow provisioning, reliable delivery/sync, labels and PGP requirements rather than the breadth of a separate webmail UI.

KyPost is the existing product foundation. The target is an integrated stack with mail reception/storage and provisioning behind its current server API, UI and clients. Android is ahead of Linux and iOS; candidate adoption must account for that gap and avoid a simultaneous client rewrite. A Mailflare fork would be assessed as an internal engine candidate, not a replacement user-facing product or merely another external mailbox connection.

Outgoing delivery must follow the root preference for an operator-owned established relay account; setup collects the operator's credentials and verifies readiness. Local mailbox storage and IMAP/SMTP client access are independent of which service delivers external mail. A relay does not guarantee inbox placement: domain authentication, reputation and abuse controls still matter. Setup must verify provider readiness (including any sandbox restrictions) and expose bounces or rejected delivery. [Gmail sender requirements](https://support.google.com/mail/answer/81126), [SES production access](https://docs.aws.amazon.com/ses/latest/dg/request-production-access.html).

Reviewed: 2026-10-03. Upstream snapshot: [`a0efd37c1078e9291de11f7e2390fe0e15c958d8`](https://github.com/hieunc229/mailflare/commit/a0efd37c1078e9291de11f7e2390fe0e15c958d8). Findings come from documentation and static source inspection; no upstream code or live account was executed.

## Recommendation

Mailflare can be an optional provider through a new JMAP adapter. It is not an existing IMAP account option. Initially describe support as experimental and limit it to explicitly verified capabilities. Full parity requires resolving custom classification keywords, incoming encrypted-message replacement, raw outgoing MIME preservation, and synchronization limits. These are implementation constraints, not just configuration work.

KyPost currently uses integer UIDs and UID-keyed results in its [mail client interface](../backend/internal/adapters/imap/client.go), while the [poller](../backend/internal/processor/poller.go) and [HTTP API](../backend/internal/api/server_userscope.go) construct cached IMAP clients. Provider selection and opaque identities therefore need changes in both paths before JMAP can be offered.

## Verified upstream capabilities

| Need | Upstream support and constraints |
| --- | --- |
| Discovery and authentication | `GET /.well-known/jmap` redirects to `/jmap/session`; Bearer key or HTTP Basic password containing a key with `jmap` scope. App passwords create such keys. Account ID is the user ID. Keys can be limited to selected mailboxes. |
| Read, search, attachments | `POST /jmap/api` supports `Email/query`, `Email/get`, `Thread/get`, `SearchSnippet/get`; authenticated blob download/upload URLs come from the Session. |
| Folders and common flags | `Mailbox/get/query/set` supports user folders; `Email/set` supports moves, read and starred flags. Messages occupy exactly one system mailbox or user folder, and cannot move between Mailflare account mailboxes. |
| Compose and send | `Email/set` creates drafts, `Identity/get` lists permitted senders, and `EmailSubmission/set` submits drafts. `Email/import` accepts uploaded RFC822 blobs into Drafts only. |
| REST alternative | `GET /api/v1/messages` requires a personal `read` key; `POST /api/v1/send` requires `send`. The send validator requires `mailboxId`, although examples in the API document omit it. |
| Notifications | JMAP `/jmap/eventsource` emits state changes by polling. Mailflare also has signed outgoing webhooks for inbound, outbound and failed events. |

Mailflare's Docker runtime exposes an **inbound SMTP listener** with AUTH disabled, and can use an **outbound SMTP relay** as a client. That listener is not authenticated SMTP submission for KyPost. No IMAP server was found in the inspected server, library and documentation trees; upstream's IMAP code is an import client, not a server. External mail clients are directed to JMAP. [Self-hosting](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/docs/self-hosting.md), [SMTP listener](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/server/runtime/smtp.ts), [IMAP importer](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/import/imap.ts), [JMAP documentation](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/docs/api.md).

## Gaps before advertising parity

- **Custom classification keywords:** JMAP only persists `$seen` and `$flagged`; `$draft` is inferred. Other keyword updates are ignored and can still return success. A KyPost adapter must explicitly reject unsupported custom labels or adopt an agreed alternative representation; silently treating success as persistence would lose classification state. [Keyword patch handling](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/jmap/emails.ts), [returned keywords](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/jmap/email-objects.ts), [import keyword handling](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/jmap/email-import-utils.ts).
- **Incoming encrypted-message replacement:** `Email/import` requires exactly one Drafts target and rejects Inbox/folders. It cannot implement replacing a received message with newly encrypted RFC822 bytes in its original folder. Folder moves do not change that import restriction. [Import target validation](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/jmap/email-import-utils.ts), [import implementation](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/jmap/emails.ts).
- **Outgoing PGP/MIME preservation:** importing a draft stores its raw bytes and downloading that draft returns them. Submission then loads parsed bodies/attachments and calls `sendEmail`, without passing the stored raw MIME. It deletes the original draft after sending. This rebuilds the message and cannot be assumed to preserve signed MIME boundaries, signatures or the `multipart/encrypted` structure. Full encrypted sending needs an upstream raw submission path or independent verified transport. [Raw draft storage/download](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/jmap/blobs.ts), [submission](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/jmap/identities.ts), [MIME parsing](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/email/parse.ts), [outbound message construction](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/email/send.ts).
- **Synchronization completeness:** `Email/changes` and `Email/queryChanges` return `cannotCalculateChanges`. Query paging works over an internally materialized list capped at 10,000 matches, with at most 250 IDs per response; a broad query cannot enumerate a larger mailbox. REST lists only the latest 100 at most and has no cursor/offset. Partitioned JMAP queries would need proof of complete coverage before being used for reliable synchronization. [Query implementation](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/jmap/emails.ts), [limits](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/jmap/constants.ts), [REST listing](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/app/api/v1/messages/route.ts).
- **IDs:** upstream uses opaque prefixed nanoid strings, not IMAP numeric UIDs or UIDVALIDITY. Integration needs stable provider IDs through KyPost's cache and client contracts. Casting or hashing these into an IMAP UID is not a safe identity contract. [ID generation](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/ids.ts).
- **Delete semantics:** upstream `Email/set destroy` moves ordinary messages to Trash, and only permanently deletes messages already in Trash or Drafts. Do not assume a single destroy permanently removes the source during replacement. [Deletion handling](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/jmap/emails.ts).

## Deployment, privacy and licensing

Cloudflare deployment stores mail in the operator's D1 database and blobs/attachments in R2; Docker uses SQLite and local files. Receiving/sending may additionally use Cloudflare, Resend or Amazon SES, while Docker can use a configured SMTP relay. This changes where plaintext is handled: encryption performed after KyPost retrieves mail does not prevent upstream providers or Mailflare from processing the original plaintext. An integration option must explain that distinction wherever users choose it. [Deployment overview](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/README.md), [provider configuration](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/docs/providers.md), [self-hosting](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/docs/self-hosting.md).

Optional outbound webhooks sign the exact JSON body with HMAC-SHA256 in `X-Email-Platform-Signature`, include delivery IDs, and retry. Inbound event payloads include message metadata rather than full raw messages. A future receiver would need signature verification and delivery deduplication, with polling/reconciliation for missed events; webhooks alone do not provide historical synchronization. [Webhook implementation](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/email/webhooks.ts), [inbound payload](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/email/inbound.ts).

Upstream includes the GNU Affero General Public License version 3. This note records the license and makes no compatibility or legal conclusion. Integrating through a separately deployed service's protocol keeps the proposed implementation independent of copied upstream code; copying, modifying or bundling upstream would require its own license review. [License](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/LICENSE).

## Acceptance evidence for a future implementation

Before promotion beyond experimental: prove enumeration beyond 10,000 messages, round-trip provider IDs, folder and flag persistence, explicit rejection of unsupported labels, and verbatim PGP/MIME delivery where promised. Incoming replacement must preserve the source until a verified replacement exists. Exercise credential revocation, retries/restarts and upstream errors against a pinned live test instance. No such runtime evidence was collected in this feasibility review.

## Fork assessment (proposed)

The requested scope is mail-server ownership, reliable sync, labels and PGP, while retaining KyPost's UI. A forked optional Docker service is a candidate: it supplies domain/mailbox routing, incoming SMTP, local storage and JMAP, while KyPost retains its classification, clients and existing accounts. This is an architectural proposal, not a migration decision. Absorbing its Node/Next/database runtime into KyPost's Go service adds a second product's lifecycle and storage model; running it separately keeps that maintenance boundary visible. Its Docker entrypoint still prepares the Next application, so extracting a headless server would be additional work. [Docker runtime](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/server/index.ts), [self-hosting](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/docs/self-hosting.md).

**A fork lets us fix the blockers; it does not arrive with those fixes.** The likely patch boundaries are:

| Priority | Proposed fork work |
| --- | --- |
| Reliable delivery | Durably record ingress before SMTP success, replay after restart, recover orphan blobs, deduplicate retries including partial multi-recipient acceptance, reconcile scheduled outbound/webhook jobs, and drain active work. SMTP does not guarantee exactly-once delivery. |
| Reliable sync | Replace the 10,000-row query ceiling with complete stable paging; add durable change records/tombstones and change-state handling, while preserving opaque IDs in KyPost. |
| Labels | Persist arbitrary validated keywords, return them through JMAP, support keyword filters, and include them in migrations/backup/restore. |
| PGP | Add verified raw-MIME submission and safe incoming encrypted replacement or encryption before durable storage; preserve envelope recipients independently from signed message bytes. |

These land in [queue/runtime](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/server/runtime/queue.ts), [JMAP email operations](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/jmap/emails.ts), [keyword serialization](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/jmap/email-objects.ts), [submission](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/jmap/identities.ts), and [intake](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/email/intake.ts). The existing SMTP-only [`Mailer.sendRaw`](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/server/runtime/mailer.ts) already passes raw bytes to Nodemailer for forwarding; reuse that mechanism before inventing another MIME builder, then verify recipient/Bcc handling, byte fidelity, authorization and retry semantics.

**Docker queue durability is a prerequisite.** Jobs and delayed retries exist only in RAM. Intake stores raw bytes before enqueueing, so a crash can leave accepted mail invisible in an orphan blob. Startup registers consumers but does not replay inbound, scheduled outbound or webhook work; the scheduler recovers assistant jobs, not these mail queues. Outbound job records persist, but their timers do not. FileBucket cannot list blobs, which also obstructs simple orphan scanning. Shutdown clears queued timers and forces exit after five seconds. These facts contradict treating “raw bytes survived” as reliable mailbox delivery. [Intake](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/email/intake.ts), [queue](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/server/runtime/queue.ts), [startup/shutdown](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/server/index.ts), [scheduler](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/server/runtime/scheduler.ts), [agent maintenance](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/agent/maintenance.ts), [outbound jobs](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/email/send.ts), [blob listing](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/server/runtime/file-bucket.ts).

**Owning the host does not automatically remove stored plaintext.** Current intake writes raw MIME, parsing writes body/snippet columns, attachments are stored separately, and FTS indexes body content. A privacy-preserving fork must cover all those copies plus queues, temporary uploads, backups and SQLite journals; encrypting the final RFC822 object alone is insufficient. Encryption before persistence conflicts with server-side body search and requires an explicit product choice about searchable metadata and where plaintext processing occurs. [Stored message fields](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/email/inbound.ts), [raw storage](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/email/intake.ts), [body search index](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/drizzle/migrations/0030_add_message_search_index.sql), [attachments](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/email/attachments.ts).

Existing plaintext backups require an explicit retention/migration policy and disclosure; a storage fix does not retroactively erase earlier copies.

Mailflare's incoming listener and SMTP relay client do not provide an IMAP server, authenticated SMTP submission server, or standalone outbound delivery to arbitrary recipient MX hosts. Plan an outbound relay/MTA and domain DNS/deliverability operations. Team account management and shared-inbox creation have explicit license entitlements; preserve those gates and establish the supported entitlement arrangement before promising multi-user provisioning. Plan an AGPL fork with required notices and corresponding-source access for remote users under section 13; copying its code into KyPost cannot simply assume KyPost's MIT license covers it. The complete combination/distribution obligations require separate review; a process boundary is not an automatic exemption. [Transport](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/server/runtime/mailer.ts), [inbound SMTP](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/server/runtime/smtp.ts), [account entitlements](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/lib/licenses/service.ts), [shared inbox gate](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/src/app/api/mailboxes/route.ts), [license sections 5 and 13](https://github.com/hieunc229/mailflare/blob/a0efd37c1078e9291de11f7e2390fe0e15c958d8/LICENSE).

Before selecting this fork, compare the same four requirements with a maintained IMAP mailbox server plus an outbound MTA/relay, which could reuse KyPost's existing mail interface. This note has not evaluated or selected such an alternative. A bounded fork prototype should first prove crash recovery, complete sync, keyword persistence and PGP/MIME fidelity; retain current IMAP support and avoid production migration until those checks pass.
